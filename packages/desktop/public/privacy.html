1. How to read this notice

Stellium is an internal team chat with live translation, used inside one company. There is no public sign-up and no general public using it. This notice covers two different groups of people, and a third group that has nothing to do with the chat at all:

  • Part A is for team members — the people who have an account and use Stellium at work. For staff, this is workplace data protection, not consumer protection.
  • Part B is for people who write to the company from outside — customers, applicants, security researchers, and anyone else who emails an address such as support@, info@, sales@, jobs@, privacy@, or security@. These people never get an account and never see Stellium; their data is processed because they contacted the company.
  • Part C is a separate, unrelated matter: visitor statistics for a different website, belonging to a business partner, which happens to run on the same server. This has nothing to do with the chat and does not concern team members or correspondents.

Sections 2–4 apply to all three groups. If you are located in the EU/EEA, the UK, or Switzerland, you may want to go directly to §4, Sending data to other countries.

3. Infrastructure, security, and who else sees data

Stellium runs on a server the operator controls, physically located in Alaska, USA. This section explains, in general terms that apply to everyone described in this notice, how data is protected and who besides the operator can come into contact with it.

3.1 How encryption is used

Data inside Stellium exists in one of three states:

  • Plain text. Readable by anyone who can access the underlying files or database directly.
  • Encrypted with a server-held key. Certain fields — message text, translations, drafts, scheduled messages, voice-message transcripts, your username and email address, poll text, AI-generated summaries, the entire support/contact mailbox, remote-access credentials, and a sales-platform token — are encrypted at rest with AES-256-GCM, derived from a master password kept on the server.
  • End-to-end encrypted. Only inside confidential channels (see §5.3). There, the server never holds a key at all.
Read this carefully

Server-held-key encryption is designed to protect data if the physical server or its storage is lost or stolen. It does not protect your messages from the operator. Whoever controls the server and the master password can decrypt and read anything encrypted this way — including message text, drafts, and voice transcripts. The only place this is not true is inside confidential channels, which use real end-to-end encryption instead (§5.3).

The following categories are not encrypted and are stored as plain text: display names (in practice, usually your real name), channel names/topics/purposes, tasks and their change history, ideas together with comments and votes on them, calendar entries including location, projects, file and attachment names (see the note on file contents below), reminder notes, the translation glossary, link previews (including the URL, page title, and preview image), status text, quiet-hours settings, how many seconds you were online each day, and all membership/relationship data — who is in which channel, who mentions whom, who reacts to what, who voted how.

We have not separately confirmed whether the contents of uploaded files and attachments (as opposed to their file names) are encrypted at rest outside confidential channels. Treat files you upload in ordinary (non-confidential) channels as visible to the operator, the same as messages.

3.3 What we do not do

Stellium does not use telemetry, crash reporting, or analytics tools of any kind, and it does not load fonts or scripts from a content delivery network or any other outside source. Software updates are checked against our own server, not a third party. The chat application itself does not log who accessed it or when.

That last point is about the application only. The network components in front of it also run software that can produce its own operating logs; at present, no maximum retention period is configured for those logs beyond a general size limit, so entries persist until that limit is reached rather than being deleted on a schedule.

3.4 Backups and physical access

Backups are taken daily and three generations are kept, but they are stored on the same physical device as the live data. They protect against an operator mistake, not against loss, theft, or failure of that device itself.

The server also has its own remote-access feature, restricted to the server owner, which shares the screen and clipboard only for as long as someone is actively watching and does not record anything. Separately, and outside of Stellium's own design, the TeamViewer software listed in the table above is installed on the same machine and provides its own, independent remote-access path.

3.1 Wie Verschlüsselung eingesetzt wird

Daten in Stellium liegen in einem von drei Zuständen vor:

  • Klartext. Lesbar für jeden, der direkten Zugriff auf die zugrunde liegenden Dateien oder die Datenbank hat.
  • Mit einem serverseitigen Schlüssel verschlüsselt. Bestimmte Felder — Nachrichtentext, Übersetzungen, Entwürfe, geplante Nachrichten, Abschriften von Sprachnachrichten, Ihr Benutzername und Ihre E-Mail-Adresse, Umfragetexte, KI-generierte Zusammenfassungen, das gesamte Support-/Kontakt-Postfach, Zugangsdaten für den Fernzugriff sowie ein Token einer Verkaufsplattform — sind mit AES-256-GCM verschlüsselt abgelegt; der Schlüssel wird aus einem auf dem Server hinterlegten Master-Passwort abgeleitet.
  • Ende-zu-Ende-verschlüsselt. Nur innerhalb vertraulicher Kanäle (siehe §5.3). Dort hat der Server überhaupt keinen Schlüssel.
Bitte aufmerksam lesen

Die Verschlüsselung mit serverseitigem Schlüssel schützt Daten, falls der physische Server oder sein Speicher verloren geht oder gestohlen wird. Sie schützt Ihre Nachrichten nicht vor dem Betreiber. Wer den Server und das Master-Passwort kontrolliert, kann alles, was auf diese Weise verschlüsselt ist, entschlüsseln und lesen — einschließlich Nachrichtentext, Entwürfen und Sprachabschriften. Die einzige Ausnahme sind vertrauliche Kanäle, die stattdessen echte Ende-zu-Ende-Verschlüsselung verwenden (§5.3).

Folgende Kategorien sind nicht verschlüsselt und liegen im Klartext vor: Anzeigenamen (in der Praxis meist Ihr echter Name), Kanalnamen/-themen/-zwecke, Aufgaben samt ihrer Änderungshistorie, Ideen samt Kommentaren und Stimmen dazu, Termine einschließlich Ort, Projekte, Datei- und Anhangnamen (siehe Hinweis zum Dateiinhalt unten), Erinnerungsnotizen, das Übersetzungsglossar, Linkvorschauen (samt URL, Seitentitel und Vorschaubild), Statustexte, Ruhezeiten-Einstellungen, wie viele Sekunden Sie an jedem Tag online waren, sowie sämtliche Mitgliedschafts- und Beziehungsdaten — wer in welchem Kanal ist, wer wen erwähnt, wer wie reagiert, wer wie abgestimmt hat.

Wir haben nicht gesondert geprüft, ob der Inhalt hochgeladener Dateien und Anhänge (im Unterschied zu ihren Dateinamen) außerhalb vertraulicher Kanäle verschlüsselt gespeichert wird. Gehen Sie davon aus, dass Dateien, die Sie in gewöhnlichen (nicht vertraulichen) Kanälen hochladen, für den Betreiber einsehbar sind — genau wie Nachrichten.

Softwareaktualisierungen werden beim eigenen Server geprüft, nicht bei einem Dritten. Die Chat-Anwendung selbst protokolliert nicht, wer wann darauf zugegriffen hat.

Das gilt nur für die Anwendung selbst. Die vorgeschalteten Netzwerkkomponenten betreiben eigene Software, die ihrerseits Protokolle erzeugen kann; derzeit ist für diese Protokolle keine maximale Aufbewahrungsdauer festgelegt, sondern nur eine allgemeine Größengrenze — Einträge bleiben also erhalten, bis diese Grenze erreicht ist, statt planmäßig gelöscht zu werden.

3.4 Sicherungen und physischer Zugang

Sicherungen werden täglich erstellt, drei Generationen werden aufbewahrt — sie liegen jedoch auf demselben physischen Gerät wie die Live-Daten. Sie schützen vor einem Fehler des Betreibers, nicht vor Verlust, Diebstahl oder Ausfall dieses Geräts selbst.

Der Server verfügt außerdem über eine eigene Fernzugriffsfunktion, die auf den Server-Eigentümer beschränkt ist, Bildschirm und Zwischenablage nur so lange teilt, wie jemand aktiv zusieht, und nichts aufzeichnet. Unabhängig von Stelliums eigenem Aufbau ist auf derselben Maschine zusätzlich die oben genannte Software TeamViewer installiert, die einen eigenen, unabhängigen Fernzugriffsweg bereitstellt.

4. Sending data to other countries

The server is in the United States. If you, as a team member or a correspondent, are located in the European Economic Area, the United Kingdom, or Switzerland, using Stellium or writing to the company means your personal data — at minimum, your email address or account details, and depending on the feature, your messages — is sent to a country outside those regions. Several of the recipients listed in §3.2 are also in the United States. Under Chapter V of the GDPR, this is a "third-country transfer" and needs its own legal safeguard, separate from the legal basis for the processing itself.

The European Commission has adopted an adequacy decision for the United States — the EU–U.S. Data Privacy Framework — which allows transfers to U.S. organizations that have self-certified under it, without further safeguards. As of the date of this notice, that adequacy decision is valid and in effect; it is being challenged before the Court of Justice of the EU, and an appeal is pending, but no ruling has been issued. Its two predecessors, Safe Harbor and Privacy Shield, were both struck down after similar challenges, so this could change. Where a recipient has not self-certified under the Framework, a transfer to it needs a different safeguard recognized under Chapter V — most commonly, the European Commission's Standard Contractual Clauses.

We have not completed a recipient-by-recipient review confirming which of these safeguards is actually in place for each U.S. recipient listed in §3.2. This notice does not claim that such a review has been completed. If you would like to know what safeguard applies to a specific recipient, write to privacy@stellium.club and we will look into it.

Die Europäische Kommission hat für die USA einen Angemessenheitsbeschluss erlassen — das EU-US Data Privacy Framework —, der Übermittlungen an dort selbstzertifizierte US-Unternehmen ohne weitere Absicherung erlaubt. Zum Datum dieser Erklärung ist dieser Angemessenheitsbeschluss gültig und in Kraft; er wird vor dem Europäischen Gerichtshof angefochten, eine Berufung ist anhängig, es liegt aber noch keine Entscheidung vor. Seine beiden Vorgänger, Safe Harbor und Privacy Shield, wurden nach vergleichbaren Verfahren beide für ungültig erklärt — das kann sich also ändern. Ist ein Empfänger dort nicht selbstzertifiziert, braucht eine Übermittlung an ihn eine andere, nach Kapitel V anerkannte Absicherung — meist die Standardvertragsklauseln der Europäischen Kommission.

Wir haben keine empfängerweise Prüfung abgeschlossen, welche dieser Absicherungen für jeden der in §3.2 genannten US-Empfänger tatsächlich vorliegt. Diese Erklärung behauptet nicht, dass eine solche Prüfung abgeschlossen ist. Wenn Sie wissen möchten, welche Absicherung für einen bestimmten Empfänger gilt, schreiben Sie an privacy@stellium.club — wir gehen dem nach.

5. Part A — Team members

This part applies to you if you have a Stellium account. Accounts are created only by company leadership; there is no self-service sign-up and no age check on account creation.

5.1 Legal basis

We process the data described in this Part on the basis of Art. 6(1)(b) GDPR (necessary for your employment or engagement) and Art. 6(1)(f) GDPR (our legitimate interest in enabling internal team communication), together with Art. 88 GDPR and, for staff based in Germany, § 26 BDSG.

The most important point for team members

Some of what is described below — how many seconds you were online each day, whether your device automatically reports the app as being in the foreground ("auto status"), your presence status, and, once introduced, read receipts — goes beyond what is strictly needed to use a chat tool and amounts to monitoring of employee behavior. Where a works council (Betriebsrat) exists or is later established, introducing or continuing to use these features is subject to its co-determination right under § 87(1) no. 6 BetrVG and should be the subject of a works agreement (Betriebsvereinbarung). As of this notice, no such agreement has been documented.

5.2 What we collect

See §3.1 for the full breakdown of what is stored in plain text and what is encrypted. In short: message content is encrypted at rest but readable by the operator; display names, channel/task/project structure, calendar entries, link previews, status text, and all membership and reaction data are stored in plain text.

5.3 Confidential channels

Confidential channels are the one place in Stellium with real end-to-end encryption (ECDH P-256 + AES-GCM): the server never holds a key and cannot read the content, regardless of the master password. Translation, AI features, search, link previews, and voice transcription are all switched off inside a confidential channel — none of them work there, because none of them can. An emergency-access mechanism exists, requiring both a release code and the channel owner's key; using it leaves a visible message in the channel, so it can never happen silently.

5.4 AI-assisted translation and other features

Outside confidential channels, translation and the other AI-assisted features described in §3.2 process your messages as described there. AI-generated task and reply suggestions can attribute responsibility for a task to a specific person and record who was mentioned in the underlying text; a suggestion you reject is not deleted and remains stored. This is the same kind of behavioral signal flagged in the callout in §5.1.

Read receipts (a signal that a message has been seen) are a feature we are planning to introduce; it is not live today. When it is introduced, we will update this notice to describe how it works — and, like presence data, it is exactly the kind of feature that may trigger co-determination rights where a works council exists.

5.5 Retention and deletion

There is currently no defined retention period for any category of team-member data described in this notice. Data is kept indefinitely unless removed by hand; there is no automated deletion process.

Deleting an account anonymizes it. It does not delete the messages that account sent, the translation memory built from them, its recorded online-time history, push-notification registrations, mentions, reactions, votes, task history, uploaded files, or pending invitations — these remain in the system, attributed to the now-anonymized record. If a channel itself is deleted, tasks and ideas that were created from it are not deleted either; they become visible to everyone rather than staying limited to that channel's former members, including a task title that originated in a private channel.

You can edit your own messages yourself for up to two hours after sending. Beyond that window, or for other categories of data, a correction requires a manual request to privacy@stellium.club.

Rights that go further than this — access, restriction, objection, and data portability — are described for every audience in §8. We do not have a self-service tool for any of them today; requests are handled by hand.

7. Part C — Visitors of a partner website

This part has nothing to do with Stellium, its team members, or its correspondents. Separately, and on the same server, the operator also measures traffic for a website belonging to a business partner. If you are reading this because you were told about it in connection with that other website, this section is for you.

No IP address is ever stored as such. Each visiting IP address is hashed (SHA-256) together with a salt value before anything is written to disk. A short-lived salt, rotated weekly, is used for day-to-day aggregate figures, so those cannot be linked from one day to the next. Separately, a long-lived salt is kept so a returning visitor can be recognized (for example, to tell a new visitor from a repeat one) for up to 730 days — meaning an individual visitor can, in principle, remain recognizable for up to two years, even though their IP address itself is never stored.

The long-lived salt and the hashed values it produces are stored in the same file. Someone with access to that file could, in principle, compute the same hash for every possible IPv4 address and match the results back to a visitor. Access to the file is restricted through operating-system file permissions; the protection is a permission setting, not a mathematical guarantee. This makes the data pseudonymous, not anonymous, within the meaning of Recital 26 GDPR. The aggregate visitor counts that the Stellium software itself displays do not include the salt or any per-visitor identifier — that figure genuinely is just a sum.

7. Teil C — Besucher:innen einer Partner-Website

Dieser Teil hat mit Stellium, seinen Teammitgliedern oder seinen Korrespondenzpartner:innen nichts zu tun. Getrennt davon, auf demselben Server, misst der Betreiber außerdem den Besucherverkehr einer Website, die einem Geschäftspartner gehört. Wenn Sie diesen Abschnitt lesen, weil man Sie im Zusammenhang mit dieser anderen Website darauf hingewiesen hat, ist er für Sie gedacht.

Es wird zu keinem Zeitpunkt eine IP-Adresse als solche gespeichert. Jede besuchende IP-Adresse wird zusammen mit einem Salt-Wert gehasht (SHA-256), bevor irgendetwas auf die Platte geschrieben wird. Ein kurzlebiges, wöchentlich wechselndes Salt dient den täglichen Summenwerten, sodass diese sich nicht von einem Tag zum nächsten verknüpfen lassen. Getrennt davon wird ein langlebiges Salt aufbewahrt, damit wiederkehrende Besucher:innen erkannt werden können (etwa um neue von wiederkehrenden zu unterscheiden) — für bis zu 730 Tage. Das bedeutet: Eine einzelne besuchende Person kann grundsätzlich bis zu zwei Jahre lang wiedererkennbar bleiben, obwohl ihre IP-Adresse selbst nie gespeichert wird.

Das langlebige Salt und die daraus erzeugten Hash-Werte liegen in derselben Datei. Wer Zugriff auf diese Datei hat, könnte grundsätzlich denselben Hash für jede mögliche IPv4-Adresse berechnen und das Ergebnis einer Besucherin oder einem Besucher zuordnen. Der Zugriff auf die Datei ist über Dateiberechtigungen des Betriebssystems eingeschränkt; der Schutz ist eine Berechtigungseinstellung, keine mathematische Garantie. Das macht die Daten pseudonym, nicht anonym im Sinne von Erwägungsgrund 26 DSGVO. Die zusammengefassten Besucherzahlen, die die Stellium-Software selbst anzeigt, enthalten weder das Salt noch eine personenbezogene Kennung je Besucher:in — diese Zahl ist tatsächlich nur eine Summe.
